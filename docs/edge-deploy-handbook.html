Start here · release operator workflow

Release reviewed code across an air gap.

edge-deploy-core publishes reviewed Autobench and Dispatch commits from GitHub to corporate Bitbucket and deploys them to Hadoop Edge Nodes — through exclusive firewall postures, interactive RSA authentication, and durable, resumable run ledgers. This handbook covers the two ways to drive a release: the engine CLI in a terminal, and the Edge Console in a browser.

What a release is

Development is normal GitHub flow — contributors and maintainers never need Bitbucket, Edge access, SSH, Kerberos, or RSA credentials. A release is the explicit operator act that takes one reviewed commit the rest of the way: Publish fast-forwards the exact GitHub commit to Bitbucket, Deploy applies it to each selected Edge Node and verifies the result, and two tag phases pin what happened on both remotes.

The invariant. GitHub main, Bitbucket main, the release tag, and the deployed Edge state must identify the same full source SHA. Every gate in the engine exists to keep those four aligned.

Run Ledger

Every release attempt is one durable Run under edge-deploy/runs/: its source SHA, per-phase and per-node state, and an append-only event log. Releases pause and resume cleanly at posture boundaries; at most one Run may be open per tool.

Engine Identity

The engine fingerprints its own installed source. A Run is bound to the engine that created it: change the engine and open Runs are orphaned — finish them with the old engine or abandon them. This is why console code lives outside edge_deploy/.

Posture

The workstation firewall has five exclusive states. GitHub write and Bitbucket/Edge access can never be held at once, so a release necessarily crosses posture boundaries. Switching is a human act — no software changes posture for you.

Transport

SSH (Paramiko) is the default per-node transport: one persistent, digest-verified connection per deploy. transport: pane is the explicit per-node recovery override that drives an authenticated tmux pane instead.

The five phases

Started on both-vpns, a guided release needs exactly one posture switch — to firewall-off for the final tag. Published release tags are immutable: never move one; publish a new version instead.

Two ways to drive it

Terminal

py -m edge_deploy release --guided --tool autobench walks every phase, prompt, and posture boundary in one invocation. Every phase is also a standalone command for surgical work. Fully supported, always available.

Edge Console

py -m edge_console serves a local web UI over the same run ledgers. Every command in this handbook is a button that runs that exact command, streams its output, and relays its prompts — including the RSA passcode. It holds no release logic and never writes a ledger (ADR-0018).

Operator-only, GitHub-clean. This package runs on the operator workstation only — Edge Nodes never import it. Generated reports, run ledgers, credentials, RSA passcodes, Kerberos passwords, tokens, and operator configuration never enter GitHub.

Network model · ADR-0012 / ADR-0013

Five postures, one at a time.

The workstation's firewall posture decides which remote is reachable. Everything about the release flow — phase ordering, pauses, the guided prompts — follows from this table.

The posture table

PostureGitHub readGitHub writeBitbucketEdge Nodes
baselineyesnonono
edge-vpnyesnonoyes
bitbucket-vpnyesnoyesno
both-vpnsyesnoyesyes
firewall-offyesyesnono
  • GitHub read (pull/fetch) works in every posture.
  • GitHub write requires the firewall off, which drops both VPNs — so GitHub write and Bitbucket/Edge access are never held together.
  • The Bitbucket and Edge VPNs are independent and may be held at once (both-vpns).

How the engine knows

The corporate proxy accepts TCP connects in every posture and only fails at the HTTP layer, so a socket test proves nothing about git. Posture is therefore verified with protocol-level git probes: git ls-remote for reads and git push --dry-run for writes (ADR-0012). Edge SSH endpoints are still TCP-probed — there is no protocol shortcut for them.

When the current posture does not satisfy a phase, the engine refuses with exactly:

phase '<phase>' requires posture [<satisfying postures>]; unreachable: <failures>.
Switch the firewall posture, then re-run: <next command>

Switching mid-release

In a guided release the engine prints the satisfying posture names and any unreachable endpoints, then stops and asks:

Switch firewall posture to [both-vpns], then press Enter to continue...

Switch the firewall, confirm, and the engine polls its probes for up to ~90 seconds while the switch propagates. If endpoints are still unreachable it re-prompts with the updated list; if a phase hits a transient remote error right after a switch (an HTTP 503 from the proxy, say), guided mode retries with 10/20/30 second backoff before giving up.

Plan for one switch. Start on both-vpns: verify runs anywhere, publish/deploy/tag-bitbucket all run there, and only the final tag-github needs firewall-off. A release started anywhere else pays extra switches.
No software switches posture. Not the engine, not the console. The console names the posture the next phase needs and shows whether it looks held — its markers are advisory; the engine's own probes are authoritative, and the switch itself is always your hands on the firewall.

The engine · py -m edge_deploy

One command per phase, one ledger per run.

The engine is a Python package driven entirely from the command line. Every phase is short, idempotent, and posture-scoped; every attempt is recorded in a durable run ledger that survives pauses, posture switches, and reboots.

Before your first release

  • Operator config installed at %APPDATA%\edge-deploy\config.yaml (first-time onboarding does this; config.example.yaml documents the shape).
  • BB_TOKEN set in the environment of every shell that runs the engine or the console.
  • A clean tool checkout on GitHub main: git pull --ff-only origin main, with green post-merge CI for HEAD.
  • Dependencies installed from the tool checkout: py -m pip install -e ".[dev,release]" (the pins live in the tool, not core — ADR-0001).
  • Node transport verified once per node (and after any SSH config change).

Transport verification is two commands:

py -m edge_deploy preflight --node node03
py -m edge_deploy transport-smoke --node node03

preflight checks DNS and TCP reachability only. transport-smoke authenticates once (this is an RSA prompt) and exercises command execution, verified file transfer, PTY dialogue, and keepalive over that single connection, then always tears it down and reports pass/fail per check.

Start or resume a run

One invocation walks every phase, pausing only for RSA passcodes and posture switches:

py -m edge_deploy release --guided --tool autobench

Press Ctrl+C (or send EOF) at any prompt to pause. The run stays open and the engine prints the exact resume command:

Paused at posture boundary. Resume with: py -m edge_deploy release --guided --run <run_id>

Resume works across postures: once verify has passed, resuming does not fetch from GitHub, so you can continue from bitbucket-vpn or both-vpns without repeating it. On completion guided mode prints release complete: <run_id> and the same summary as status.

The non-guided wrapper chains phases until the first posture boundary, saves state, prints the posture message, and exits 0 — re-run after switching:

py -m edge_deploy release --tool autobench
# … switch posture when told, then …
py -m edge_deploy release --run <run_id>

Or run each phase yourself — status always prints the next command with the posture it needs:

py -m edge_deploy verify --run <run_id>
py -m edge_deploy publish-phase --run <run_id>
py -m edge_deploy deploy --run <run_id> --nodes node03,node04
py -m edge_deploy tag-bitbucket --run <run_id>
py -m edge_deploy tag-github --run <run_id>

Starting a new release while an unresolved run exists is refused, with both ways out — continue or abandon — spelled out in the refusal. At most one run may be open per tool.

Watch the state

py -m edge_deploy status

With an active run, status prints per-phase state and the next command:

run run-20260703T120000Z-aa6d9a5  tool=autobench  kind=release  source=aa6d9a5  created=2026-07-03T12:00:00+00:00
  verify:        passed
  publish:       passed (snapshot bb7c8d1)
  deploy:        node03=passed node04=failed
  tag_bitbucket: pending
  tag_github:    pending
next: py -m edge_deploy deploy --run run-20260703T120000Z-aa6d9a5 --nodes node04   [posture: both-vpns]

status reads local ledgers only. It works in every posture and is the one command that still answers when everything else refuses.

The verify gate

Verify is where the engine decides the commit is releasable. Two checks, both hard:

GitHub CI, exactly this SHA

A successful post-merge run of the CI workflow for the exact source commit on main. The engine asks gh run list first and falls back to the GitHub REST API using the credential git's own helper already holds — gh is convenient, not required. The fallback is consulted only when gh could not answer at all: an answer from gh is final in both directions, and an unknown never reads as a pass.

The tool's own gate

The source checkout's committed tools/dev/local_check.ps1. The tool owns test selection and parallelism; the engine owns ordering and evidence. Only a successful exit records passed tests; a failure writes a redacted tail to verify-local-check.log and blocks every later phase.

Publish normally reuses the run ledger's verification instead of repeating the local check — but only when the evidence is bound to the run's exact source SHA with successful CI and passed tests. An incomplete ledger safely falls back to running the check again. --no-local-check bypasses only that publish fallback; verify always runs the source-bound tool gate.

Deploy and the RSA prompt

Deploy opens one persistent, digest-verified SSH connection per node and reuses it for authentication, dependency transfer, rollout, and drift checks. Enter the RSA passcode at the interactive prompt when asked; the progress heartbeat shows >>> WAITING FOR OPERATOR - … while the engine waits on you. Matching dependency archives already on the node are reused by digest without moving bytes; new archives stream with live progress (MiB sent, percent, MiB/s) to the terminal and to release-progress.json, which the console renders as a progress bar.

Deep smoke. --smoke deep (on release, deploy, and rollback) runs the tool's deeper smoke checks on the node and may prompt for a Kerberos password the same way deploy prompts for RSA. Use it when the tool profile declares deep smoke support.

After completion

  • Both tags exist and status --run <run_id> reports complete.
  • The audit record is on Bitbucket's release-log branch (appended by tag-bitbucket).
  • Bump the pinned edge-deploy-core version in each tool's pyproject.toml through a normal GitHub pull request — only after the new engine tag is published.

The cockpit · py -m edge_console · ADR-0018

Every command is a button. Every prompt reaches you.

The Edge Console is a local web UI over the run ledgers of the tool checkouts you point it at. It runs the engine's own commands on your behalf, streams their output live, and relays the prompts the engine blocks on — including the RSA passcode. It holds no release logic, never writes a ledger, and never switches posture.

Launch it

The console is deliberately not pip-installed — editing it must never change Engine Identity — so run it from the core checkout:

cd D:\edge-deploy-core
py -m edge_console --root D:\autobench --root D:\robocop

It binds to loopback only and opens http://127.0.0.1:7643/.

FlagMeaning
--rootTool checkout containing edge-deploy/runs; repeat to watch several. Defaults to the current directory.
--github-write-rootCheckout used for the GitHub write probe; defaults to the --root paths.
--portListen port (default 7643).
--read-onlyWatch only: every button disabled, commands still visible and copyable. Onboarding always launches it this way.
--demoFabricated checkouts driven by an offline simulator — the whole flow, prompts included, with no network and no credentials. The safest way to learn the console.
--engine-pythonInterpreter used for python -m edge_deploy (default: the one running the console). It must match your terminal interpreter, or runs created on one side are refused by the other on Engine Identity.
--no-browserDo not auto-open a browser tab.
Environment matters. Every command the console runs inherits the console process's environment — so BB_TOKEN must be set in the shell that starts it, exactly as it must for a terminal release.

What the page shows

Live runs, spotlighted

An open run leads the page: its phase rail, live progress, one action row per legal next step, and a terminal streaming the engine's output. Terminals survive re-renders — scroll position and a half-typed passcode included.

Release decision cards

Every watched checkout with no run in flight gets a verdict, the three commits it rests on (nodes, checkout, GitHub main), a precondition checklist with a button beside each fixable item, and one Start guided release call to action.

History

Closed runs collapse into history. Each completed release offers a rollback to its own tag — only when no run is open in that checkout.

Posture panel

The five postures, which one looks held, and per-endpoint reachability lamps. Advisory only: the engine's probes decide, and switching stays manual.

Prompts, relayed

The engine's operator boundaries are recognised by their exact text and rendered as typed prompts:

  • the RSA passcode — a masked field written straight to the process stdin, never stored, never logged, shown only as asterisks in the transcript;
  • a Kerberos password (deep smoke) — the same way;
  • the guided posture boundary — the posture name plus one “I have switched” button;
  • any [y/N] gate — a yes/no pair;
  • and, as a safety net, any other question the engine prints and then waits on gets a generic answer box, so an unrecognised prompt can never hang a run silently. The console cannot know that answer is not a password, so it is masked like one.

Refusals you see coming

Conditions that already sit on disk or in the console's environment are stated before you press anything, and disable exactly the actions they would stop — scoped to the phases the run has not passed yet. Among them: a run created by a different engine build, a lock another process holds, a missing or unreadable operator config, BB_TOKEN absent, a checkout off main / dirty / drifted off the run's reviewed commit / with remotes that do not match its edge_deploy.yaml, a missing local_check.ps1 or no PowerShell, an unset audit_repo or queued audit records, ledger nodes no longer in the operator config, and non-green GitHub CI.

CI is the one networked prediction. A known non-green answer (failed, pending, or no run for the SHA) disables verify and release like any other predicted refusal. An answer the console could not get blocks nothing — the engine's gate still decides. The console runs the engine's own probe, so on any answer they both have, prediction and gate cannot disagree.
Paramiko only. A node configured transport: pane takes its RSA passcode in the tmux pane, which the console can neither see nor answer — so deploy, release, rollback and transport-smoke are refused for that node with a pointer to the terminal. preflight is TCP-only and still works. Pane remains the documented recovery override (ADR-0011); it is just not driven from here.

The safety model

  • Loopback bind, a loopback Host check on every request, and a per-process token embedded in the page — no other origin can read a ledger or press a button.
  • Every button maps to one entry in a closed allowlist and runs with a fixed argument list — nothing the browser sends can become shell syntax, a new flag, or a different program.
  • Checkouts must be ones the console was started with; run ids, node names, tags, commits, and tool names are pattern-checked server-side; one command per checkout at a time.
  • Training ledgers are refused by the server, not just hidden. Release commands are refused outside a git checkout.
  • Secrets are written to one child process and dropped: never stored, never logged, masked in the transcript, never returned by any endpoint.
  • Stopping a command closes the child's stdin first, so the engine unwinds and releases its own run lock; force-taking a lock needs a dialog naming the pid and host that hold it.

When it stops · locks, resumes, rollbacks

Nothing is lost. Read the refusal, then resume.

The engine is built to stop safely: every pause leaves an open run that resumes exactly where it stopped, and every refusal names its reason and, usually, the next command. Fix the first concrete error; do not improvise around a gate.

Pause and resume

Ctrl+C (or EOF) at any guided prompt pauses the run. It stays open, the lock is released, and the engine prints the resume command. Resuming skips phases that already passed; once verify has passed, resuming does not even need GitHub.

The exact refusals

run <run_id> is locked by PID <pid> on <hostname>…

Another process holds the run lock. If it is a live engine (or a console-driven one), let it finish — two engines in one run corrupt it. Only when you know the holder is dead, re-run with --force-lock; the console offers the same thing as Take the lock and resume, behind a confirmation naming the pid and host.

release refused: unresolved run <run_id> … exists

At most one run may be open per tool. Continue it (py -m edge_deploy release --run <run_id>) or abandon it with a recorded reason. The refusal prints both commands.

phase '<phase>' requires posture […]; unreachable: …

Not an error — a boundary. Switch the firewall to a listed posture and re-run the printed command. Endpoints can fail transiently for up to a minute while a switch propagates.

Verify refuses: no successful GitHub CI run for the commit

The gate wants a green post-merge CI run for exactly the release SHA on main. Wait for CI, or fix and merge again. If gh is missing the engine already fell back to the REST API by itself; if neither could answer, the refusal keeps the diagnosis — an unknown never passes.

Verify or publish fails the local check

Read the redacted tail in verify-local-check.log (or publish-local-check.log) inside the run directory. The tool's committed gate failed for its own reason; correct it and re-run the same phase. No Bitbucket mutation happens before the gate passes.

Engine identity mismatch: the run was created by a different engine build

Any engine source change orphans open runs. Finish the run with the engine that created it, or abandon it and start fresh with the new engine. The console detects this before you press anything.

The console refuses a node: pane transport

By design — the pane's RSA prompt lives in tmux where the console cannot answer it. Drive that node from a terminal; everything else about the run stays console-drivable.

Drift detected on a node

Something on the node no longer matches the released snapshot. Investigate before releasing on top: py -m edge_deploy drift --node <node> --commit <sha> lists the differing files. A drifted node is a finding, not an automatic rollback.

Rollback

py -m edge_deploy rollback --tag release-20260707T153012Z-41d9b0c

Rollback restores a previously recorded successful release tag by starting a new run that forward-deploys the old snapshot. It never rewinds Bitbucket main and never moves a published tag — tags are immutable. The console offers it from the completed run it would restore, in history, only while no run is open in that checkout.

Abandon

py -m edge_deploy abandon --run <run_id> --reason "<why>"

Closes an open run with a recorded reason. Nothing already deployed is rolled back (ADR-0003) — if nodes received the release before you abandoned, decide separately whether to roll them back.

Artifact hygiene

Local means local. Run ledgers, generated reports, logs, credentials, RSA passcodes, Kerberos passwords, tokens, and operator configuration never enter GitHub. The audit trail that is shared lives on Bitbucket's release-log branch, appended (redacted) by tag-bitbucket.

Shared language · CONTEXT.md

Say it the way the ledger says it.

These terms have exact meanings in the engine, the console, and the ADRs. When a refusal uses one of them, this is what it means.

Release Operator
The person who explicitly releases merged GitHub main. The only role that touches Bitbucket, Edge, RSA, or Kerberos.
Tool
One deployable product: Autobench or Robocop/Dispatch.
Tool Profile
The tool's committed edge_deploy.yaml: node-independent release metadata, no operator paths or credentials.
Publish
Fast-forward the exact reviewed GitHub commit to Bitbucket. Never a rewrite.
Deploy
Apply the published commit to each selected Edge Node and verify final commit, drift, permissions, and smoke checks.
Release
One operator-controlled publish-and-deploy run for the tool in the current checkout.
Rollback
Explicitly restore a previously recorded successful release tag. Never rewinds Bitbucket main.
Snapshot
The exact source tree a release or rollback delivers. Every deployed-state judgement — drift included — is against the snapshot's tree, never the operator's working tree.
Posture
The workstation's firewall state, one of five (ADR-0013). Switching is a human act.
Run
One durable release attempt, from creation to complete or abandoned. At most one open run per tool.
Run Ledger
The durable, append-audited record of a run: source SHA, per-phase and per-node state, and the engine identity that created it.
Engine Identity
The exact content of the installed release engine. A run is bound to the engine that created it; any engine change orphans open runs.
Guided Release
A release in which one engine invocation walks the operator through every posture switch and RSA prompt instead of exiting at each boundary.
Edge Console
The local web UI over the run ledgers of the watched checkouts. Runs the engine's own commands, streams output, relays prompts; holds no release logic, never writes a ledger, never switches posture (ADR-0018).
Action allowlist
The closed set of engine commands the console can run. Every button maps to one entry with validated parameters; nothing else is constructible from the browser.
Decision card
The console's per-checkout release verdict: the three commits it compares, a precondition checklist, and one call to action that disables itself with a stated reason.
Predicted refusal
A condition the console can already see (on disk or in its environment) that would make the engine refuse — shown before the button is pressed, scoped to the phases it would actually stop.
Authenticated Pane
The local tmux/psmux session holding an authenticated SSH connection to one Edge Node. A lossy, screen-scraped text channel — not a byte pipe.
Pane-Safe
A remote command or payload that survives the pane's known corruptions: single-line, quote-stripping, length limits, screen-wrap. Arbitrary content crosses base64-encoded between digest-verified sentinels.
Drift
A difference between runtime-critical files in the released commit and the files present on an Edge Node.
Training run
An onboarding run against a sandbox ledger, explicitly marked training. The console displays it read-only and its server refuses to act on it.
Demo mode
py -m edge_console --demo: fabricated checkouts and an offline engine simulator. Prompts and refusals behave like the real thing; nothing real is attached.

The invariant, one more time

GitHub main == Bitbucket main == release tag == deployed Edge state. All four must identify the same full source SHA. Everything else in this handbook is machinery to keep that true.
